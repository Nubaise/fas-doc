# Phase 13 — Faculty UI

## Overview

Phase 13 implements the faculty-facing web interface for the Faculty Appointment System (FAS).

The Faculty UI provides authenticated faculty users with a dedicated portal for managing their profile, availability, exceptions, and appointments.

The implementation uses the existing backend APIs and follows the frontend architecture established during Phase 11 and the Student UI patterns established during Phase 12.

## Goals

- Build the faculty dashboard.
- Build faculty profile management.
- Build weekly availability schedule management.
- Build availability exception management.
- Build faculty appointment management.
- Support appointment lifecycle actions allowed by the backend.
- Protect faculty routes through the existing authentication and authorization flow.
- Provide appropriate loading, empty, error, and success states.
- Reuse the existing frontend API client, query layer, routing, and UI architecture.
- Maintain responsive and accessible interfaces.

## Faculty Dashboard

The faculty dashboard provides an overview of the faculty user's current appointment activity.

It includes:

- Faculty welcome message.
- Today's appointment count.
- Pending appointment request count.
- Upcoming confirmed appointment count.
- Navigation to availability, appointments, and profile management.
- Empty states when there are no upcoming appointments.

The dashboard determines the current faculty member from the authenticated user's identity and existing faculty data.

## Faculty Profile

The faculty profile interface allows a faculty member to view and update their profile information.

Faculty users can edit:

- First name.
- Last name.

The following information remains controlled by the system:

- Employee number.
- Department.

The UI provides:

- Existing profile data loading.
- Editable first and last name fields.
- Disabled system-controlled fields.
- Save state.
- Success feedback.
- Error handling.

The backend remains responsible for enforcing which faculty fields may be modified.

## Availability Management

Faculty users can manage their recurring weekly availability schedules.

Each schedule supports:

- Day of week.
- Start time.
- End time.
- Slot duration.
- Active/inactive state.

Supported slot durations are:

- 15 minutes.
- 30 minutes.
- 45 minutes.
- 60 minutes.

The faculty UI does not allow students or faculty users to create arbitrary appointment durations. Appointment slots continue to be generated by the backend from faculty availability configuration.

The interface supports:

- Creating schedules.
- Editing schedules.
- Activating/deactivating schedules.
- Deleting schedules.
- Loading states.
- Empty states.
- Error feedback.

The backend remains responsible for schedule validation and overlap protection.

## Availability Exceptions

Faculty users can manage exceptions to their normal availability.

The interface supports:

- Full-day exceptions.
- Partial-day exceptions.
- Creating exceptions.
- Editing exceptions.
- Deleting exceptions.

Partial-day exceptions contain:

- Date.
- Start time.
- End time.

The backend remains responsible for validating exception conflicts and applying exceptions when generating available appointment slots.

## Faculty Appointments

The faculty appointments interface groups appointments by lifecycle state.

The UI provides sections for:

- Pending requests.
- Confirmed appointments.
- Appointment history.

Faculty users can open individual appointment details.

The appointment detail interface displays the available appointment information returned by the backend and provides lifecycle actions according to the appointment's current state.

## Appointment Lifecycle Actions

Faculty users can perform the following actions where permitted by the backend:

### Pending

- Accept.
- Reject.

### Confirmed

- Reschedule.
- Complete.
- Cancel.

The UI does not independently define appointment lifecycle rules. The backend remains the source of truth for authorization and valid state transitions.

## Rescheduling

Faculty rescheduling uses backend-generated availability.

The faculty user selects from available appointment slots rather than entering an arbitrary appointment duration.

The existing availability API is used to retrieve valid slots for the selected date.

The selected slot is then submitted through the existing appointment rescheduling endpoint.

## Routing

Faculty routes are protected by the existing application authentication and routing structure.

Faculty UI routes include:

- Faculty dashboard.
- Faculty availability.
- Faculty appointments.
- Faculty appointment details.
- Faculty profile.

The implementation reuses the existing frontend router and authentication context.

## API Integration

The Faculty UI uses the existing centralized frontend API client.

API integrations include:

- Faculty data.
- Availability schedules.
- Availability exceptions.
- Appointments.
- Appointment lifecycle actions.

No new business rules are implemented in the frontend.

The frontend consumes the existing backend contracts and relies on the backend for authorization, validation, slot generation, conflict detection, and appointment lifecycle enforcement.

## Query and Mutation Handling

TanStack Query is used for server-state management.

Relevant query data is invalidated after successful mutations so that the faculty UI reflects the latest backend state.

This includes:

- Faculty data after profile updates.
- Availability schedules after schedule mutations.
- Availability exceptions after exception mutations.
- Appointments after appointment lifecycle actions.

## UI States

Faculty UI screens provide appropriate states for:

- Initial loading.
- Empty data.
- API errors.
- Successful mutations.
- Pending mutations.

Destructive actions use confirmation where appropriate.

The current implementation uses the existing UI primitives and patterns from the frontend foundation and Student UI.

Further visual refinement and design-system polish remain part of Phase 15.

## Backend Controller Validation Fixes

During Phase 13 integration testing, several backend controllers were corrected to work with the project's global `StandardSchemaValidationPipe`.

The affected controllers were:

- Faculty controller.
- Availability schedules controller.
- Availability exceptions controller.
- Appointments controller.

The controllers now use typed `@Body()` DTO parameters while the global validation pipe handles schema validation.

This preserves the existing architecture and prevents validation schema objects from being incorrectly passed into controller body handling.
